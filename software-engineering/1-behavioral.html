Data platform (TD Securities)


# Conflict

Situation: In Nov 2025 I was leading the effort to provision a self-service data platform for TD Securities.
While we were preparing the production deployment, my manager asked us to open the DEV environment to users first.

Concern: We were pushing changes to DEV constantly as we rolled out features, so users could hit instability
and lose trust in the platform.

Action: I asked my manager and the team for a call so we could talk in person. I listened first. My manager's point
was that users were urgently waiting for something they could try. We agreed on three guardrails:
  1. Onboard only the first 5 to 10 pilot users, who already knew Databricks.
  2. Treat DEV as a sandbox, with no real data.
  3. Keep each user inside their own catalog (logical separation with Unity Catalog in Databricks).

Result: The pilot users were happy to start in DEV. The roughly 150 users who later joined production gave my team

# Ambiguity / Trade-off

Situation: I was lead engineer on the TD Securities data management team, which owned a platform where users
ingest and consume data. In Oct 2025 I was asked to provision a self-service data platform. My team was a project manager,
a front-end developer, and a back-end developer. The platform was an internal React and Java app, with infrastructure on
Databricks and Azure Data Lake Storage. I planned the work over three months. In mid-November my manager told me it had to be
done in two weeks.

Task: Deliver a working platform in two weeks without breaking the bank's controls.

Actions: I proposed trade-offs that chose speed over tech debt.
  1. Architecture: we had designed micro-services, but I proposed a monolith. Micro-services would have meant multiple repos and
     multiple release pipelines, which are error-prone at the bank, and would have cost months.
  2. Process: I streamlined PR approvals and moved to fast merges.
  3. Stakeholders: I aligned with the team that owns the change-order process and got VP approval. I also escalated the
     network request that let users reach our Databricks instance, which cut the SLA from one week to one day.

Result: We deployed infrastructure in the first week and the API in the second. We expected about 40 internal users and about 150
came within the first month. Executive leadership praised how fast we enabled the platform.

Model testing (Layer6 AI)


# Ownership

Situation: In Dec 2024 I was an ML engineer at Layer6 AI on the MLOps and ML platform team. We computed batch inference with custom Python
packages whose dependencies were updated often for security patches. New package builds sometimes broke code running in production.

Task: No one asked me to fix it. I wanted to detect breakages before they reached production.

Actions: I built three chained pipelines in Azure Data Factory that run automatically:
  1. Retrieve the run IDs of the last inference and ground-truth jobs generated by the current package.
  2. Run new inference and ground-truth jobs with the updated package.
  3. Compare the outputs of the two runs and verify the checksum.

Result: Failures caused by dependency updates were caught before any inference job ran in production.

Cost saving on ML serving pipeline (Layer6 AI)


# Impact / Leadership

Situation: In Dec 2023 at Layer6 AI, all ML use cases ran dataprep on Azure Databricks all-purpose clusters. Those clusters stay up through an
inactivity period before shutting down, and we paid for that time. Job clusters terminate as soon as the job finishes.

Obstacle: We used Azure Data Factory to trigger Databricks jobs, so the natural fix was to configure job clusters in the Data Factory UI.
But TD's process required every Data Factory change to go through an internal pipeline and a change order. Doing that for each use case
would have taken significant time.

Action: I designed a workaround. Instead of configuring job clusters in Data Factory, I store configuration files in DBFS. When a job runs,
it reads its configuration file, then creates and runs the cluster through the Databricks API. So instead of one Data Factory change per
use case, we deployed a single notebook in Databricks that writes the configuration files. I proposed it and the team accepted it.

Result: The team adopted job clusters. Savings were $47-70K per year for each production use case. With 7 batch use cases that is roughly
$0.42-0.63M a year. [FILL: confirm currency and that figures are annual]

Elasticsearch upgrade (Layer6 AI)


# Impact / Project deep dive

Situation: In mid-2022 at Layer6 AI, my team stored inference and ground-truth data in Elasticsearch for an internal application. The cluster ran
on 3 virtual machines, on version 6 (the free version, with no authentication). Writes took over 3 hours during inference and ground-truth
runs, and the disk was nearly full.

Task: Upgrade from version 6 to 8, completed in Dec 2022.

Design:
  Capacity estimate for the next 5 years.
  Deployed on Kubernetes for autoscaling and closer integration with the inference jobs, which already ran there.
  Hot nodes with more compute and less storage, cold nodes with less compute and more storage.
  Split each index into shards of at most 600 MB for parallel reads.
  Replicated each index across different data nodes for availability.
  Took periodic snapshots to a storage account for reliability.

Problem: Restoring a version 6 snapshot into version 8 worked in DEV but failed in production because of data size. During the
production change window I researched alternatives, found reindexing (which moves data over the network), tested it in DEV, then applied it
in production.

Result: The migration finished within the change window. Read and write performance improved about 2x.

# Failure

Situation: I owned upgrading Elasticsearch from 6 to 8 at Layer6 AI.

What went wrong: I tested the upgrade in DEV by following the migration documentation: snapshot the old cluster, restore into the new one.
That worked, so I took a production snapshot and prepared to restore. During the production change, the restore failed. My test data was
much smaller than production, so my test did not prove the plan would work.

Recovery: I researched other migration methods during the change window, learned about reindexing, tested it in DEV, and used it in production.
I completed the migration within the window.

Log4J (Layer6 AI)


# Trade-off

vulnerability that allowed remote code execution. My team at Layer6 AI owned the ML platform, with 7 production models.

Decision: I proposed shutting down all running models in production immediately. Our models were batch models, so their inference results can be
recomputed at any time. The cost of shutting down was no inference output for a few days. The cost of staying up was exposure to remote code execution.

Actions: I shut down all the containers, patched them with a newer version of Log4j, and redeployed them by Monday night.
